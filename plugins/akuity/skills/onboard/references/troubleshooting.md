# Onboarding troubleshooting

Symptom-first. Most of these are silent misconfigurations with exact fixes — check here before retrying a call.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Warehouse never produces freight, no error anywhere | Missing `spec.shard`, the warehouse landed outside the project's namespace (the platform apply defaults an omitted `metadata.namespace` to `kargo`, not the project), the image's tags are not semver and the subscription kept the default `SemVer` strategy, or the registry is private and the project has no image credential | Set `spec.shard` to the Kargo agent name; set `metadata.namespace: <project>`; set an explicit image selection strategy (`NewestBuild`, `Lexical`); have the user create the image credential (labeled Secret via `akuity kargo apply`, or `kargo create repo-credentials … --image …` with instance access — see `pipeline-facts.md`) |
| Warehouse reports `Unable to discover artifacts: … AllowTags is deprecated and unsupported as of v1.11.0; use AllowTagsRegexes instead` (or the same for `IgnoreTags`) | The subscription uses the pre-1.11 tag-filter fields, which still apply cleanly but fail at discovery — older Kargo examples all show `allowTags`, so generated manifests reach for it | Re-apply the warehouse with `allowTagsRegexes` / `ignoreTagsRegexes` — both are **lists of regexes**, unlike the old fields (`pipeline-facts.md`) |
| Warehouse discovered several image tags but produced Freight only for the newest, or the user's Stage matrix needs an older version | Automatic Freight creation uses the best current artifact set; `discoveryLimit` exposes candidates in `status.discoveredArtifacts` but does not create one Freight per candidate | Collect the full Stage-to-version matrix, temporarily narrow the image subscription with `constraint` or an exact `allowTagsRegexes` until each required Freight exists, then restore the intended ongoing subscription (`pipeline-facts.md`) |
| An image subscription's version constraint applies but discovery ignores it on Kargo v1.11 | It uses the removed image field `semverConstraint`; the correct image field is `constraint` (`semverConstraint` still exists in other subscription types, which makes copying examples misleading) | Read the instance version's Warehouse CRD and re-apply the image subscription with `constraint` |
| Promotion fails at `git-clone`, or at `git-push` with `could not read Username for 'https://github.com'` | The Kargo Project has no matching git credential, or it lacks the needed permission. A private repo needs read access at clone; every Promotion needs write access at push | Have the user create or fix the git credential (labeled Secret via `akuity kargo apply`, or `kargo create repo-credentials … --git …` with instance access), then promote the same Freight again; the errored Promotion needs no cleanup |
| Promotion fails at its last step, after git already updated | The `argocd-update` step is missing a link: the Kargo agent has no `spec.data.remoteArgocd`, or the Application lacks `kargo.akuity.io/authorized-stage: "<project>:<stage>"` | Add the missing link, then retry the promotion — git is already correct |
| An earlier Stage becomes unhealthy after a later Stage promotes successfully, while all Applications are synced and healthy | Several Stage applications track the same branch and every `argocd-update` pins its health check to that Stage's pushed commit; a later push advances the shared branch | For a shared branch, omit the source `desiredRevision` and let the app-only `argocd-update` drive and check the sync operation. If exact revision pinning is required, isolate Stages with separate branches or immutable sources (`pipeline-facts.md`) |
| Promotion rejected outright | The stage has no `spec.promotionTemplate.spec.steps` | Add the promotion steps |
| Kargo instance apply rejected with "requested remote argocd instance is being deleted", or the referenced Argo CD instance is no longer listed | The Argo CD instance did not finish provisioning, or it was referenced before it reported healthy | Re-apply the Argo CD instance, wait until it reports healthy, read its current id, then re-apply the Kargo agent with that id |
| Kargo Project, Stage, Freight, and Promotion tools return `Internal error occurred (reference: …)` on a healthy instance, while the platform instance read/apply still work | The instance has neither the admin account nor OIDC configured. The instance read shows `apiCm.adminAccountEnabled` absent or false and no OIDC config | The user enables the admin account and sets a password under **Settings → System Accounts**, configures **Settings → OIDC Config**, or applies the config declaratively (`instance-access.md`). Verify the instance read shows the config and a cheap Kargo read succeeds, then retry |
| Kargo tools return an internal error on a healthy-looking instance | The instance was created with the literal `spec.version: latest` | Recreate, or have an administrator fix, the instance with `spec.version` omitted |
| Platform-endpoint in-instance tools are denied with "not permitted to use this tool on the instance it names, or MCP is not enabled for that instance" | MCP access is off for that instance (`mcpServer.enabled`), or the caller lacks the per-instance permission — instances created through the platform MCP endpoint have access enabled automatically, pre-existing ones often do not | Enable MCP access for the instance (spec update, or its Settings → MCP Access page); if it is already on, the caller needs the instance permission from their org admin |
| A private repo's app won't sync, or the warehouse can't reach the repo | Credential missing on one side: Argo CD and Kargo do not share credentials | Argo CD needs its own repository-credential Secret; Kargo needs its labeled credential Secret in the project — both shapes and commands in `pipeline-facts.md` |
| Kargo ignores a credential Secret that applied cleanly | The Secret lacks the `kargo.akuity.io/cred-type` label, or landed outside the project's namespace — apply accepts both, Kargo silently never uses them | Re-apply with the label (`git` or `image`) and `metadata.namespace: <project>` |
| One document in a multi-document apply failed (e.g. `context deadline exceeded`) while its siblings succeeded | The apply is per-document, not atomic, so a partial success is possible | Re-apply only the failed documents — apply is upsert, so this is safe |
| A cluster or direct Kargo-control-plane registration ignores fields, or validation falls through to an unrelated required field after trying a guessed wrapper | The manifest shape was inferred instead of taken from the live apply schema; the public declarative-spec docs do not define every MCP-specific cluster wrapper | Stop trying field variants. Read `official-docs.md` and the live tool contract; if neither gives the exact shape, ask the user to register it in the portal or switch the control resources to direct-apply mode |
| Registered cluster stays unhealthy | The agent is not actually installed in the user's cluster yet | Run (or have the user run) `akuity argocd cluster install-agent …`; health follows the install |
| `install-agent` runs for minutes with no output and creates nothing in the cluster | Its output was piped or filtered, which silently wedges it | Kill it and rerun unpiped, in the background, with output redirected to a log file; read the log |
| Agent pods in the user's cluster show `ImagePullBackOff` | The cluster cannot pull the agent image from Akuity's registry (egress or registry policy) | Fix the cluster's egress/registry access; if it persists, contact Akuity support |
| The akuity CLI fails with `Unauthenticated … token is expired` mid-run | The stored login token expired | `akuity login --server https://<portal-host>` again, then rerun the command |
| An instance endpoint that worked starts returning 401 | The instance token expired (native tokens default to a 24h TTL) | Header-registered endpoint: re-mint and re-register per `instance-access.md`. Browser-login session: `/mcp` → authenticate again — these sessions have no refresh token. Neither is a platform failure |
| A `claude mcp add`-registered server never shows tools in the session | Added from a different directory (local scope is per-directory), added mid-session (needs a session restart), or the connection dropped (needs a manual reconnect) | Re-add from the session's own directory; restart the session; `/mcp` → reconnect — see the registration gotchas in `endpoints-and-auth.md` |
| Platform endpoint rejects calls with "the MCP server is not enabled for this organization" | The org-wide platform-endpoint toggle is off, or MCP access is unavailable for the organization | An Organization Owner or custom role with Organization update permission enables it under Organization Settings → MCP Access; if the page is unavailable, contact an Akuity representative or support |
| `/mcp` on an instance hostname returns 404 | MCP not enabled for that instance: organization access is unavailable, or the instance spec lacks `mcpServer.enabled: true` | Enable it in the instance spec (`spec.instanceSpec` / `spec.kargoInstanceSpec`) or the instance's Settings → MCP Access page; if **MCP Access** is unavailable, contact Akuity |
| Instance MCP login offers no browser flow, or its OAuth discovery 404s | The instance has neither SSO nor password auth enabled — no IdP, and no enabled admin/local account, so there is nothing to advertise | Configure the admin account per `instance-access.md` — the endpoint then serves a browser password login — or register with a bearer-token header |
| Argo CD instance endpoint's interactive login opens a browser but is rejected with a `redirect_uri` error | A recent MCP access change has not finished publishing, the client is not using a `localhost` loopback callback for Dex, or the direct OIDC callback is not registered | Wait for the instance to finish reconciling and retry. For Dex, use a loopback callback on the `localhost` hostname. For direct OIDC, have the identity provider administrator register `https://ARGO_CD_HOSTNAME/mcp/oauth/callback` on the public OAuth client shown in **Settings → MCP Access**, or register the endpoint with a bearer-token header (`instance-access.md`) |
| Permission denied on an instance endpoint | The instance's own RBAC (Argo CD `policy.csv`, Kargo's Kubernetes RBAC) denied the logged-in instance user | Report it as an authorization answer; the user needs a grant from their instance admin — do not retry |
| Instance hostnames don't resolve, or the akuity CLI targets the wrong portal | Non-production or self-hosted platform: the hostnames must resolve from this machine, and the CLI talks to whatever portal it was logged into | Fix DNS/hosts for the instance hostnames; re-run `akuity login` against the right portal before the agent install |
