# akp-platform quickstart layout (GitOps mode)

Read this only when the user chose the akp-platform layout at round one. Instances, clusters, the `kargo` destination, credentials, round two, and promotion approval are the shared GitOps steps in `../SKILL.md`; this file holds the akp-platform deltas.

github.com/akuity/akp-platform is Akuity's quickstart repo: one root app-of-apps (`bootstrap/platform-aoa.yaml`), two ApplicationSets that discover `apps/<name>/argocd/` and `apps/<name>/kargo/` from git, shared `CustomPromotionStep`s under `kargo-shared/`, and four sample guestbook apps covering the promotion matrix — Kustomize or Helm, promotions committing to `main` or pushing rendered manifests to `rendered/<app>/<stage>` branches. Adding an app is one directory (`docs/onboarding.md`); `bootstrap/` never changes. **Offer it only when a pipeline is in scope**: two of the sample patterns have no deployable source until a promotion creates their `rendered/<app>/<stage>` branch, and the sample `env/` files carry `latest` placeholders that only a promotion overwrites — an app-only scope can neither pin them from round one nor sync them at step 8. Deltas:

- **Two extra prerequisites.** (1) The repo's Warehouses and Stages carry no `spec.shard`, so the Kargo instance needs `spec.kargoInstanceSpec.defaultShardAgent` set to the agent's **id** (not its name); the apply rejects it until the agent exists, so send it as a second Kargo apply once the agent is listed (it need not be healthy yet). The `apply_kargo_instance` tool description still states the shard rule without this exception — it predates `defaultShardAgent`. Without it every Warehouse sits idle with no error, and the instance list reads do not echo the field — verify by Freight appearing. (2) The fork keeps the name `akp-platform` and stays public (Argo CD and Kargo read it anonymously; a private fork needs the Argo CD repository credential and the Kargo git credentials before anything syncs or promotes).
- **Phase one — fork, personalize, push, bootstrap — before round two.** User-owned, from their clone: they fork `akuity/akp-platform` and run `personalize.sh`, which rewrites every `example-org` URL, the workload cluster name, the Kargo destination name, and optionally the guestbook image org. It asks exactly four questions on stdin — GitHub owner, workload cluster name, Kargo destination name, GHCR org (blank keeps `ghcr.io/akuity`) — and with fewer answers it exits 1 having rewritten nothing, so the non-interactive form is exactly four lines: `printf '<github owner>\n<cluster name>\nkargo\n\n' | ./personalize.sh`. Keep the default `kargo` for the third answer unless the user needs another name: the script rewrites the Kargo destination only in `bootstrap/kargo-apps.yaml`, so any other name leaves `bootstrap/kargo-shared.yaml` pointing at a cluster that does not exist, and the shared `CustomPromotionStep`s never sync — edit that file's `destination.name` by hand in the same commit. It is one-shot: re-running needs `git checkout -- .` first, which also restores any sample directories already deleted, so delete samples after personalizing. It takes **one** workload cluster name and puts every stage of every app on it in namespaces `<app>-<stage>`; a round-one map with several clusters means editing the per-stage destination in each `apps/<name>/argocd/appset.yaml` — say so, do not pretend the map is honored. Their own app enters as `apps/<name>/`, copied from the closest sample per `docs/onboarding.md`, but this first commit carries only its control files — `argocd/appproject.yaml`, `kargo/project.yaml`, and `kargo/warehouse.yaml` (subscribed to their image); manifests, overlays, Stages, and tasks wait for phase two: the Warehouse must exist before round two can show discovered versions, so this push cannot wait for approved versions. Sample app directories they do not want are deleted here (bootstrap prunes them). Then apply only `bootstrap/platform-aoa.yaml` through the platform Argo CD apply — an `applications` entry with project `default`, source path `bootstrap`, destination `name: in-cluster` / namespace `argocd`, automated sync with prune and self-heal. Within a minute the ApplicationSets create `argocd-<app>` and `kargo-<app>`, and the Projects and Warehouses arrive by sync into the `kargo` destination — step 5 is done and round two can start. Expected states, not failures: the rendered-branch sample apps report `ComparisonError … unable to resolve 'rendered/<app>/<stage>' to a commit SHA` until their first promotion creates the branch; the commit-to-`main` sample apps sit OutOfSync/Missing until their first promotion (no automated sync, exactly as step 8 wants); `kargo-shared` reports `no matches for kind CustomPromotionStep` only on a Kargo without the `ee.kargo.akuity.io` group, and nothing else depends on it.
- **Phase two — after the Stage-to-version plan, one more commit.** Add everything the stage apps need to render and promote: the app's manifests (`base/` for Kustomize, `chart/` for Helm — the `env/<stage>` overlays and values reference them; copy the sample's namespace mechanism whole and do not mix them: the Kustomize samples ship a `Namespace` object in `base/` that each overlay renames and set only `destination.name`, the Helm samples set `destination.namespace` with `CreateNamespace=true` and ship no Namespace — step 7's bare Deployment + Service is not enough for the Kustomize shape), its `env/<stage>` files pinned to the approved versions, `argocd/appset.yaml` (one Application per stage, `authorized-stage` annotations, no automated sync), `kargo/stages.yaml`, `kargo/tasks.yaml`, and any `kargo/analysis.yaml` a Stage's `verification` references. This is steps 7, 8, and 9 in one commit; the ApplicationSets pick the new files up on sync. A commit-to-`main` pattern then holds valid desired state in git before any promotion, as step 7 requires; a rendered-branch pattern cannot — its state exists only once promoted — so steer a user who wants pre-promotion desired state in git to a commit-to-`main` pattern. A rendered pattern then needs the **new Freight this commit produces**: its Warehouse also subscribes to `main` under `includePaths: apps/<name>`, and its task clones `commitFrom(vars.repoURL).ID` — the Freight's commit, not the branch tip — so the Freight round two showed, pinned to the phase-one commit, fails in `kustomize-build` / `helm-template` with the `env/<stage>` or `chart/` path missing however complete `main` is. Re-read the project's Freight after the commit, reconfirm the Stage-to-version plan against it, then promote. That Freight bundles the newest discovered image tag with the new commit, so a plan holding an older version for some stage (`prod=v1, staging=v2`) still has no usable Freight for `v1` — the existing one pins the phase-one commit. Run step 6's loop again **after this commit**: narrow the image subscription so the older version is the best match, wait for its Freight (the Warehouse pairs it with the current tip, which now has the sources), repeat per version, then restore the subscription. The commit-to-`main` patterns clone `branch: main`, so any Freight renders the current sources and this does not apply.
- **Credentials are per Kargo Project** — one for each sample kept, plus one for their app. Every sample PromotionTask pushes (to `main` or to a `rendered/*` branch), so even a public fork fails at `git-push` without them. Use the labeled Secret command from `references/pipeline-facts.md` once per project, `metadata.namespace: <project>`, `repoURL` exactly `https://github.com/<owner>/akp-platform.git`. The repo's own `add-credentials.sh` is not a substitute: it hardcodes the four sample projects, never the user's app, needs a `kargo` CLI login, and exits at the first project that no longer exists. The README's "Option B" — one shared credential in a `kargo-shared-resources` namespace — additionally needs `spec.kargoInstanceSpec.globalCredentialsNs` and agent secret-sync; offer it only if the user asks for it.
- **Round two and promotion run per project.** Read that project's Freight, plan, promote `dev → staging → prod` — for a rendered pattern on the Freight carrying the phase-two commit, as above; the `guestbook-rendered` staging Stage carries a sample verification gate that must pass before prod accepts the Freight.
